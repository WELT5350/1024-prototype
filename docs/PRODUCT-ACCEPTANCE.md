# 产品验收迭代

目标：在已经可运行的证据台上补齐产品判断与辨识度。不是增加页面数量，而是让用户看清楚“已知什么、缺什么、补证为什么改变判断、同事下一步怎么用”。

## 本轮计划

1. **准确显示缺口**：区分原文支撑与来源有效性。只缺日期时保留主体、用途、服务适配的原文支撑；但在来源日期确认前仍为待核实，不能交接。过期或日期冲突的证据，不能借用另一条无关来源变为有效。
2. **补证前后对照**：记录实际改变的字段，以及规则建议、原文支撑、来源状态和人工结论的前后变化。明确规则建议改变不等于人工已确认。保留旧版日志，不编造过去没有记录的细节。
3. **三行交接卡**：说明做什么业务、哪些原文支撑、下一步核实什么。仅使用已录入字段与原文编号；预算、用量、采购窗口没有采集就明确未知。可复制、下载和随证据包导出。

## 验收场景

- 澄野数据仅缺日期：三项原文支撑保留；来源待核；规则建议待核实。补齐日期后原文支撑仍是三项，仅来源状态改变，规则建议成为候选，需人工重新确认。
- 同一企业有近期官网和过期的模型 API 职责：不能因为官网有效，就把过期职责当成近期服务需求。
- 核实画像或导入新证据，同样留下变更对照；没有实际变化则不撤回旧结论、不产生假日志。
- 复制的三行卡能够独立说明业务、依据与未知项。工具技能、代招、私有部署、过期来源不被包装成已确认采购需求。
- 备份恢复保留新对照；旧备份仍能读，旧日志没有字段快照就明确不提供对照。
- 桌面与手机能直接找到核查操作；对照和交接卡不会造成横向溢出。

## 完成标准

- [x] 新语义与交接准入回归测试通过
- [x] 新增、编辑、导入、画像变更均保留真实对照
- [x] 三行交接卡的边界用例与复制/导出通过
- [x] 桌面和手机实际操作检查通过
- [x] 演示视频、运行说明、架构及验证记录同步
- [x] PR 与主分支 CI 通过，交付包更新

本轮按上述场景和可观察行为验收。真实效率和商业价值仍需实际用户验证。
